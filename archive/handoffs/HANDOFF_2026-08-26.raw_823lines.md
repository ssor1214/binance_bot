## 1. P0 사고 3건 — 전부 "봇이 손절 없이 포지션을 들고 있었다"

### 사고 A. 안 1(손절폭 ROE 5% 상한)이 `-2021`을 유발했다 → 원복

어제 넣은 신규 진입 손절폭 상한이 손절선을 **진입가 쪽으로 당긴다**. 지정가 체결 직후
SL을 거는 사이 가격이 조금만 움직이면 거래소가 `-2021 Order would immediately trigger`로
거부한다. 거래소 SL이 없으니 봇 폴링(10초)만 남고 그동안 손실이 벌어진다.

```
SL 등록 실패(-2021)   배포 전 0건/31진입(0%)  ->  배포 후 16건/107진입(15%)
손절 -6% 초과 비율    배포 전 6%  ->  배포 후 18%   (최악 -18.76%, 24초 만에 -10.24%)
그 9건 합계 -20.80  =  밤샘 손실 -60.53 의 34%
이 9건이 없었다면 순손익 -25.54 -> -4.75
```
**큰 손실을 막으려던 장치가 무방비 포지션을 만들어 더 큰 손실을 냈다.**
→ `--new-max-stop-roe 0` 으로 원복(사용자 승인). 채택 경로(`--adopt-max-stop-roe 5`)는
진입 직후가 아니라 안정된 포지션에 걸려 `-2021`이 안 나므로 **유지**.

### 사고 B. 체결된 진입주문이 재시작으로 증발 → 고아 무보호 포지션

`taskkill /F`는 `atexit`을 건너뛴다. 그래서 진입 지정가 주문이 살아남아 **재시작 뒤에
체결**되는데, `entry_orders`는 메모리에만 있어 새 프로세스가 그 주문을 모른다.
상태파일에도 없으니 채택에서 `채택 제외(e2 소유 아님)`로 빠지고 **영구 무보호**가 된다.

실사고: ONGUSDT(10:06 체결), 이어서 POL/STAR/STX/VIRTUAL 4건이 **SL 0건**으로 방치.

### 사고 C. 봇이 12분간 freeze — REST 타임아웃이 없었다

```
11:19:06  ONGUSDT 지정가 전량 체결(1277주)
11:19:06  상태파일 마지막 갱신 ← 이후 정지
11:27:48  런로그 마지막 줄     ← 이후 정지
11:31:00  CPU 25초 동안 0.078초  ← 사실상 정지
          => ONGUSDT 13분간 손절 없음
```
`Client(...)`에 `timeout`이 **어디에도 없었다**. python-binance는 requests를 쓰는데
timeout이 없으면 커넥션이 끊긴 채 응답이 안 올 때 **영원히 블록**된다.
죽지 않았으니 아무도 되살리지 않았다.

> 사용자가 "텔레그램에 ONGUSDT가 안 잡힌다"고 알려준 것이 발견 경로였다. 표시 버그가
> 아니라 봇이 그 체결을 인식할 기회 자체가 없었던 것이다.

### 대응 — 3겹 방어

| 층 | 대응 시간 | 막는 것 | 코드 |
|---|---|---|---|
| REST 타임아웃 10초 | 10초 | 네트워크 블록 | `bot/exchange.py` `requests_params={"timeout": 10}` |
| 미추적 포지션 안전망 | 75초 | 원인 불문, 손절 없는 포지션 채택 | `reconcile_live_positions()` |
| 메인 루프 워치독 | 180초 | 원인 불문, 봇 자체를 되살림 | `start_main_loop_watchdog()` |

추가로 **진입주문을 상태파일에 보존**(`entry_orders` 전체 dict)하고 기동 시 복원한다.
심볼 목록만 저장한 1차 수정은 불충분했다 — order_id/side/stop이 있어야 체결 확인이 된다.

**워치독 설계**: e3는 supervisor가 없어 **자가 재기동**한다. 하트비트(`beat()`)를 메인
사이클과 분 정렬 내부 루프 **양쪽**에 찍는다(정상 대기를 freeze로 오판하지 않도록).
발동 시 로그 → 봇 락 해제 → 같은 인자로 DETACHED 프로세스 기동 → `os._exit(9)`.
`os._exit`이 atexit을 건너뛰지만 진입주문은 상태파일에 있으므로 유실되지 않는다.
격리 테스트로 재기동 체인(gen0→gen1→gen2, PID 변경)을 실제 확인했다.

**안전망 구멍도 고쳤다**: 초기 구현이 `sm in entry_orders`면 무조건 건너뛰어서, 체결
확인 경로가 막히면(=사고 C) 안전망이 스스로 비켜섰다. 이제 주문 발주 후
TTL+30초가 지나도록 해소가 안 되면 안전망이 가져간다.

## 2. 채택한 변경 4건

### ④ 같은 방향 3슬롯 제한 (`--max-same-side 3`)

오전에 **7슬롯이 전부 SHORT**였다. 크립토는 BTC에 동조하므로 분산이 아니라
**한 베팅의 7배 레버리지**다. 원장 168건 실측:

```
같은방향 0~2개 보유 중 진입   130건(77%)  승률 53.1%  건당 -0.113
같은방향 3개 이상 보유 중 진입  38건(23%)  승률 36.8%  건당 -0.423
=> 거래의 23%가 손실의 52%.  막으면 -30.78 -> -14.71 (적자 52% 축소), 거래수 -23%
```
**롱에도 걸었다.** 롱 편중은 3건뿐(5%)이지만 그 3건 전부 손절이고 건당 -0.816으로
숏(-0.410)보다 나쁘다. 롱이 안전한 게 아니라 이 원장 구간이 하락장(숏비중 58~76%)이라
롱이 몰릴 기회가 없었을 뿐이다. 상승장이 오면 대칭으로 발생한다.

미체결 진입주문도 센다 — 안 그러면 한 사이클에 주문만 5개가 나가고 체결 뒤에야 편중이 드러난다.

### ⑥ 눌림 깊이 상한 0.5% (`--max-pullback-pct 0.5`)

캐시 132건에서 후보 지표 7개를 재보니 **6개가 유의하고 전부 "작을수록 좋음"** 이었다
(눌림깊이 r=-0.344 / ATR r=-0.328 / 목표거리 r=-0.296 / HullMA기울기 r=-0.266 / 손절폭 r=-0.191).
서로 다른 지표가 아니라 **"얼마나 크게 움직였나"라는 하나의 축**이다.
추세가 강할수록 좋을 거라 본 `HullMA 기울기`마저 반대로 나왔다.

```
없음(현행)   132건 100%  승률 43.2%  건당 -0.36%
눌림 <=0.5%  104건  79%  승률 50.0%  건당 +0.39%    A그룹 +0.41% / B그룹 +0.38%
```
**임계값 선정 근거는 과적합 저항력이다.** 심볼 반분 교차검증에서 A/B가 거의 동일하다.
더 조인 0.4%는 A -0.03 / B +0.87로 완전히 갈라져 과적합이 명백했다. 복합조건
(눌림0.6+ATR1.4)이 점 추정치는 +0.69%로 높지만 A/B 격차가 0.37로 벌어져 기각했다.

### ⓐⓑ CM 지정가 TP 재배치 (`--cm-tp-pullback-pct 0.5`, `--cm-tp-max-roe 6`)

**사용자 제안**에서 나왔다("예측한 TP에서 -0.5%도 어려운가").

```
ⓐ 앞당김 0.2 -> 0.5%   TP체결 47.1% -> 65.4%,  승률 50.0% -> 65.4%,  건당 +0.39% -> +0.65%
   (1.0%까지 키우면 수수료를 못 넘어 -0.18%. 0.5~0.7이 최적 구간)
ⓑ TP 상한 ROE 6%      먼 목표를 안 기다리고 상한에서 끊는다.  건당 +0.86%
ⓐ+ⓑ                  건당 +1.04%   A그룹 +1.05% / B그룹 +1.03%  (격차 0.01)
```
**격차 0.01은 오늘 잰 것 중 가장 견고하다.** 반대로 현행(앞당김 0.2%)은 격차가 1.65로
가장 크고 B그룹에서는 -0.32%로 마이너스였다 — 즉 현행 +0.39%는 A그룹 운에 기댄 값이었다.

**거래수 불변**이라 원칙 1과 완전히 무관하다. `cm_tp_price()` 안에서만 끝나는 변경이다.

근거의 뿌리는 실원장이다: 등록된 TP 목표 ROE와 성적의 상관 **r=-0.261 (t=-2.67, n=100)**,
목표 ROE 8% 이상 8건은 **승률 0%, 건당 -1.611**. 먼 목표는 "많이 벌 자리"가 아니라
"도달 못 하고 되돌아올 자리"였다.

### 신호창 5초 -> 10초 (`--max-signal-age 10`)

`age = time.time() % 60`, 즉 **매 분의 앞 N초**에만 진입을 허용하는 게이트다.
5초면 창이 8.3%뿐인데 루프 주기가 10초라 절반 가까운 분은 창에 못 들어갔다.

**진짜 원인은 스캔 소요시간이다.** 진입 로그의 '초' 분포:
```
0~4초 100건  |  5~9초 58건  |  10초+ 5건
```
85심볼 1회전에 약 10초가 걸려 **스캔 뒷줄 심볼이 신호 품질과 무관하게 구조적으로 영구 탈락**했다.

> **경과 기록(중요)**: 처음 20초로 넓히면서 "3분봉이라 20초 지연은 품질에 영향 없다"고
> **근거 없이 단언**했다. 사용자가 "품질 저하는 없냐"고 물어 재보니 실제로 있었다:
> `age 0~5초 120건 승률53.3% 건당-0.080` vs `5~20초 34건 승률35.3% -0.580`,
> STOP 비중 48%→69%. 다만 원장의 `entered_at`은 **주문 시각이 아니라 체결 확인 시각**이라
> "신호가 낡은 주문"과 "체결이 늦은 주문"이 섞여 인과를 가리지 못했다. 같은 심볼끼리도
> 방향이 엇갈린다(ONG·ZEC은 5초+가 좋고, TUT·TRUMP는 나쁨).
> **결론이 안 나면 안전한 쪽**으로 10초를 택했다. 10초면 스캔의 97%를 커버하고,
> 20초로 넓혀서 더 얻는 건 5건뿐이라 위험 구간만 늘린다.

**미해결 딜레마**: 근본 원인이 스캔 속도라 게이트를 조이면 원칙 1, 넓히면 원칙 2를 해친다.
제3의 길(**스캔 순서 무작위화** / 스캔 분할 / poll 단축)을 검토해야 한다. 순서 무작위화가
특히 유망하다 — 지금은 같은 심볼이 항상 뒷줄이라 영구 배제되는데, 무작위화하면 게이트를
안 넓히고도 모든 심볼에 기회가 돌아간다.

## 3. 기각한 것 3건 — **이쪽이 더 중요하다**

오늘 제안 중 셋이 검증에서 뒤집혔다. 앞의 둘은 **코드를 쓰기 전에** 걸렀다.

### ③ "TP 목표 ROE 2% 미만이면 진입 포기" — 폐기

어제 캐시에서 좋아 보여 제안했는데, **실원장이 정반대**였다.
가까운 목표(ROE 0~1%)가 승률 79.2%로 가장 안전하고 먼 목표가 재앙이다(r=-0.261).
캐시 시뮬만 믿고 넣었으면 손해였다.

### B "사이클 내 후보 스코어링/정렬" — 기각, 미구현

사용자 요청으로 3단계(원장 검증 → 점수 정의 → 정렬 시뮬)를 밟았다.
```
선착순(현행)     124건 승률 44.4% 건당 -0.22%   <- 현행이 최고
눌림 얕은 순     124건 승률 42.7% 건당 -0.40%
변동성 낮은 순    124건 승률 43.5% 건당 -0.35%
엄선할수록 나빠짐: K=1 -0.55% / K=3 -0.40% / K=6 -0.33%
```
**사이클당 평균 후보가 2.4개뿐이라 경쟁 자체가 없다.** 132건 중 124건(94%)이 어차피
통과하니 정렬이 자르는 건 8건뿐이고, 그 8건을 잘못 잘라 오히려 나빠졌다.
편중은 한 사이클에 몰려서가 아니라 **여러 사이클에 걸쳐 누적**되므로 접근 자체가 문제와 안 맞는다.
→ 대신 **절대 임계값**(⑥)이 답이었다.

### 안 3 "손절 하한 ROE 3%" — 기각

하한으로 **새로 열리는 거래만** 따로 재니 건당 -0.33%로 여전히 마이너스였다
(승률 55.2%, 손절률 24.5%로 좋아 보여도). 거래수를 늘리는 건 마이너스를 곱하는 것이다.
라이브 실측 `근접손절 55%`로, 캐시 시뮬의 93%는 과대추정이었다.

## 4. SL 개선 시도 — 전부 탈락 (검증 함정 기록)

사용자 요청으로 손절 개선을 찾았으나 **캐시로는 답이 안 나온다**는 게 결론이다.

### 함정: 손절폭 확대는 "손절 없음이 최고"로 수렴한다

```
EMA25(현행) 손절률 27.9% 건당 +1.04%
ATR 1.0배   22.1%  +1.23%
ATR 2.0배   10.6%  +1.52%
ATR 5.0배    2.9%  +1.59%   최악 1건 -30.08%
손절 없음     0.0%  +1.63%   <- 단조 수렴
```
**캐시 5.5시간에 큰 추세 역행이 없다**는 뜻이지 개선이 아니다. 보유시간을 135분으로
늘리면 손절 없음이 +2.64%까지 올라가는데 같은 착시다. **손절폭은 이 데이터로 못 정한다.**

### 본전이동/트레일링 — 효과 0

```
없음 +1.04% / 본전이동 ROE+3%→+1% +1.06% / 트레일링 최고점-3% +1.05% (발동 0건)
```
TP 상한 ROE 6%를 넣은 뒤로는 대부분 익절에서 먼저 끝나 발동 여지가 없다.
어제였다면 의미가 있었지만 지금은 TP가 그 역할을 대신한다.

### 손절 후 쿨다운 — 근거 없음

직전 손절 후 30~45분 재진입이 오히려 건당 +0.429이고, **직전 익절 후가 -0.408로 더 나쁘다.**
패턴이 없다.

주기오류 0 / 워치독 0

멈춘" 첫 사례**다. 테스트 통과가 라이브 안전을 보장하지 않는 유형이 있다.

**2) 워치독이 이 유형을 못 잡는다 (미해결, 감시 대상).**
정렬 대기 루프의 beat 가 메인 사이클 정지를 가려준다. 사고 C 대응이 만든 사각지대다.

## 14. 저녁 감사 (18:40~19:00) — 사용자 화면 발견 3건 + 싱크버그 1건

**전부 사용자가 화면에서 이상을 짚어 발견됐다.** 로그만 봐서는 못 찾았을 것들이다.

### ① "TP 설정이 안 되고 있어" — 절반은 표시 문제, 절반은 진짜

**표시**: 봇은 SL 과 TP 를 **다른 주문 유형**으로 건다.
```
SL -> CONDITIONAL(STOP_MARKET)  -> 바이낸스 포지션 행의 "TP/SL" 칸
TP -> LIMIT reduceOnly          -> "미체결 주문(Open Orders)" 탭
```
포지션 행만 보면 TP 칸이 비어 보인다. **의도된 설계**다 —
reduceOnly LIMIT 이라야 청산이 maker(0.02%), 포지션 행 TP/SL 은 taker(0.05%).

### ② 부분체결 잔량 미취소 -> 유령 추가 진입 (내가 만든 회귀)

```
VVVUSDT: 25.48 주문 -> 11.46 부분체결 -> 안전망이 채택하며 추적 종료
         -> 잔량 14.02 가 거래소에 살아남아 나중에 체결 (reduceOnly 아님 = 포지션 증가)
```
정상 체결 경로에는 *"부분체결이면 잔여 지정가가 살아 있다. 취소하지 않으면 추적 수량과
실제가 어긋난다"* 는 주석과 함께 취소 코드가 **원래 있었다.**
오늘 안전망 경로를 만들면서 그 방어를 옮기지 않았고, 안전망이 주 경로(유입의 93%)가
되면서 상시 열려 있었다. -> 안전망도 `NEW`/`PARTIALLY_FILLED` 면 취소하도록 수정.

### ③ "진입하자마자 1초 만에 컷" — 체결가 기준 손절폭 미검증

```
18:46:14 진입 BTRUSDT LONG 평단0.089721 손절0.089340
18:46:15 손절선 이미 통과(-2021) - 즉시 시장가 청산
18:46:17 ROE -3.61% net -1.8465  보유 3초
```
손절폭 = 0.42% = **ROE 2.12%**. `--min-stop-roe 3.5` 를 통과할 수 없는 값이다.

원인: **게이트·손절선·체결이 서로 다른 시점을 본다.**
게이트는 '계획 진입가'로 검사하는데 지정가는 나중에 다른 가격에 체결된다
(LONG 은 목표가 이하). 체결가가 손절선에 가까워지면 실제 손절폭이 줄고,
SL 등록 시점엔 이미 지나간 상태가 되어 `-2021` 이 난다.

즉시청산 8건 실측:
```
보유 3~6초 (진입 직후)          3건  -6.31   <- 손실의 대부분
보유 4~53분 (재등록 실패)        5건  -2.48
합계 -8.79 (오늘 손익의 15.2%, STOP 전체의 4.9%)
```
-> **체결 시점에 손절폭을 재검증**해 체결가 기준 `min_stop_roe` 미만이면 그 거리까지 넓힌다.
   진입 여부는 안 바뀐다(원칙 0/1 무관). 좁은 손절이 나쁘다는 355건 실측과 방향 일치.

### ④ 싱크버그 — 원복시킨 안 1 이 뒷문으로 되살아나 있었다

```
1948행  재시작 채택 경로  -> adopt_max_stop_roe (5)   O 의도대로
2852행  안전망 경로      -> adopt_max_stop_roe (5)   X 봇 자기 진입에도 적용
3585행  정상 진입 경로    -> new_max_stop_roe   (0)   O 의도대로
```
1절에서 **사용자 승인으로 `--new-max-stop-roe 0`(상한 없음)으로 원복**한 안 1 이,
안전망이 주 경로가 되면서 **채택용 상한 5%로 사실상 부활**해 있었다.
상한은 손절선을 진입가 쪽으로 당기므로 `-2021` 의 직접 원인이다.
-> `_cap = new_max_stop_roe if _ours else adopt_max_stop_roe` 로 경로별 분리.

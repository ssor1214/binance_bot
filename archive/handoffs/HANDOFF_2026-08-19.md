```

                          캐시 60초 -> ratio  5.0 (스파이크 판정)
```

방아쇠: 체결 워커가 `WS_TRADE_PREEMPTIVE_RESTART_SEC=300`으로 5분마다 예방 재시작해서
캐시가 절대 안 찬다. **즉 이 봇의 스파이크 판정은 상시 오탐 상태였다.**

-> `min_baseline_coverage=0.8` 가드 추가. 테스트 `test_spike_partial_baseline.py`
(옛 코드에서 4건 실패 확인). 함께 발견: 워커가 `detect_volume_spike`를 기본값으로 호출해

**주의**: `WS_TRADE_PREEMPTIVE_RESTART_SEC(300)` == `SPIKE_ENTRY_BASELINE_SEC(300)`이라
스파이크 기능은 **구조적으로 동작 불가**다. 지금은 정직하게 `insufficient_baseline`(항상 False)로

고치려면 재시작 주기를 늘리거나 baseline을 줄여야 하는데, WS 레이어는 python-binance
read-loop freeze 이력이 있어 **테스트넷 장시간 검증 없이 건드리지 말 것**.


**우위는 존재하지만 13.7%에만 있다**:
```
무장 성공  86건(13.7%)  승률 98.8%  명목당 net +1.0566%   합 +7.999
무장 실패 543건(86.3%)  승률 61.3%  명목당 net -0.2101%   합 -11.349
```

## 9. 매시 정각 브리핑에 반드시 포함할 것

### 실행 순서
```
1) python scripts/reconcile_realized_pnl.py --hours 6 --write     # 반드시 먼저
2) PYTHONIOENCODING=utf-8 python scripts/hourly_breakdown.py --markdown
3) PYTHONIOENCODING=utf-8 python scripts/analyze_arming_rate.py --since "2026-08-18 07:55:42"
```
`estimated_pnl_usdt`는 폴링 시점 mark price 추정치라 체계적 편향이 있다.
반드시 `net_realized_usdt`로 집계하고 추정값은 괄호 병기.

### 최상단 표 (필수)
- **이번 1시간**: 거래수 / 승률 / 롱승률+건수 / 숏승률+건수 / 순익
- **인수인계 이후**(exited_at >= mktime("2026-08-17 12:26:20")): 거래수 / 승률 / 롱 / 숏 / 순익 / 시간당 / 경과시간
- **원복이후 누적**(>= mktime("2026-08-14 12:09:30")) 한 줄
- **총자산**: `ex.get_total_margin_balance()` API 원본. 로그의 "총자산" 줄은 가용잔고라 신뢰 금지

```
stop_dist_pct = stop_roe / leverage
atr_pct < stop_dist_pct * min_atr_vs_stop_ratio -> 진입거부
```
즉 `STOP_LOSS_PCT`만 바꾸면 **진입 종목이 같이 바뀐다.** 손절 6.0→3.0에서 거래수가 314→1,403건으로 늘었다. §5의 "손절폭 축소 기각"이 이 교란을 탔을 가능성이 크다. 손절폭만 비교하려면 ATR 대역을 절대값으로 고정해야 한다(`MIN/MAX_ATR_VS_STOP_RATIO`를 6.0/새값 배율로 조정).

## 23. WS 설정 버그 — 라이브 봇도 영향 가능성

**e1에서 WS 캐시가 절대 채택되지 않았다.** 원인 3개, 셋 다 고쳐야 한다:

1. **seed 히스토리 1개 부족**: `ws_worker`가 `limit=min(history_len, 99)=99`로 seed하는데
   `get_klines`가 미완성봉 1개를 버려 **98개만** 들어간다. `has_sufficient_history(sym, 99)`가
   1개 차이로 영원히 False. -> `WS_KLINE_HISTORY_LEN=150`
2. **신선도 기준이 봉 주기보다 짧다**: 1분봉은 확정 캔들이 60초에 한 번 오는데
   `WS_KLINE_MAX_STALENESS_SEC=20`이라 대부분의 시간 동안 `is_fresh`가 False. -> `90`
3. **대기 시간 부족**: `last_update_ts`는 WS 확정 캔들이 와야 갱신된다. seed(10~15초)만으로는
   부족하고 최대 60초를 더 기다려야 한다. -> 기동 후 100초 대기

**라이브 `.env`도 `WS_KLINE_MAX_STALENESS_SEC=20`이다.** 라이브 봇 역시 WS 캐시를 못 쓰고
REST로 폴백해 왔을 가능성이 크다. 라이브 재가동 시 확인할 것.

## 24. REST 순회 지연 — WS 전환의 실측 근거

문턱 1.5 신호는 **해당 1분봉이 확정된 60초 동안만 유효**하다. REST 순회로는 놓친다:
```
85심볼 x 스로틀0.35초 = 한바퀴 30초 + poll 20초 = 50초
40심볼 x 스로틀0.15초 = 한바퀴  6초 + poll 15초 = 21초
```
실측: 4분간 40심볼을 28회 순회하며 BTWUSDT가 7번 문턱을 충족했으나, 봇은 그 순간 다른 심볼을
보고 있어 1시간 동안 신호 0건이었다. WS 전환으로 순회 지연 자체를 제거했다.

## 27. 슬롯 상한 — 자동 사이징의 두 번째 정정 (2026-08-20)

슬리피지의 트레이드오프). 실제 원장으로 확인 후 조정할 것.

## 35. 3분할이 실제로 분할이 아니었던 버그 (수정 완료)

**증상:** `--tranches 3` 이 EMA5·10·15 세 터치를 **전부 기다린 뒤 평균가로 한 번만**
진입했다. 분할매수가 아니라 "진입 지연"이었다. 1·2차 구간의 기회를 통째로 버렸고,
3차 터치가 안 오면 아예 진입하지 않았다.

**수정:** 터치마다 목표수량의 1/N을 **각각 실주문**한다.
- `pending[sym]["done"]` 으로 이미 집행한 차수를 기록, 새 터치가 생긴 주기에만 주문
- 이미 보유 중인 심볼도 `len(pos.legs) < tranches` 면 추가 진입 허용
- 추가 진입 시: 기존 거래소 손절주문 취소 → 수량 합산 → **평단 기준으로 손절(EMA25)·
  익절(BB / 1:2) 재계산** → 전량 기준 손절주문 재등록
- 청산 시 `pending` 도 함께 정리(안 하면 다음 사이클에 유령 차수가 남는다)

2026-08-20 실거래에서 2차·3차 진입 로그를 확인했다.

## 36. 1차 투입 최소금액 — `--min-leg-margin` (기본 3.0)

**문제:** 슬롯 8 × 3분할이면 잔고 32 USDT에서 1차 투입이 약 1.2 USDT였다.
여기서 4% 올라도 절대금액이 남지 않는다. 최소명목(5.0 USDT)에도 미달해 주문이 거부됐다.

**해결:** 슬롯 수를 "1차당 증거금 ≥ min-leg-margin" 이 되도록 역산한다.

```python
need_per_leg = max(min_notional / leverage * 1.12, min_leg_margin) * tranches
slots = max(1, min(int(bal * max_exposure // need_per_leg), max_concurrency))
size  = max_exposure / slots
margin = bal * size / tranches      # 1차당 증거금
```

| 잔고 | 슬롯 | 1차 증거금 | 1차 명목(5배) | 3차까지 채웠을 때 운용률 |
|---|---|---|---|---|
| 32 | 3 | 3.48 | 17.4 | 98% |
| 40 | 4 | 3.27 | 16.3 | 98% |
| 60 | 6 | 3.27 | 16.3 | 98% |
| 100 | 8 | 4.08 | 20.4 | 98% |
| 200 | 8 | 8.17 | 40.8 | 98% |

잔고가 늘면 슬롯이 자동으로 늘어난다(상한 `--max-concurrency 8`).
**노출은 0.98로 둔다.** 1.0으로 하면 손절 체결·수수료 차감 직후 가용증거금이 음수가 되어
2·3차 주문이 거부된다.

## 37. 치명적 운영 사고 — 봇이 6개 동시 실행되고 있었다

Git Bash 의 `ps aux | grep ... | xargs kill` 은 Windows 의 python.exe 를 **죽이지 못한다.**
게다가 `ps aux | grep -c` 가 0을 반환해 "죽었다"고 오판하게 만든다.
그 결과 재시작할 때마다 인스턴스가 쌓여 **구버전 4개 + 신버전 2개가 각자 실주문**을 냈다.
1차 투입이 1 USDT로 쪼개진 진짜 원인이 이것이었고, 중복 진입도 발생했다.

죽은 봇이 남긴 **고아 WS 워커 4쌍**도 계속 살아서 같은 캐시 파일을 물고 있었다.

**앞으로 봇 종료/재시작은 반드시 PowerShell 로 한다.**

```powershell
# 확인
Get-CimInstance Win32_Process -Filter "Name like '%python%'" |
  Where-Object { $_.CommandLine -match 'scalp_bot|ws_worker' } |
  Select-Object ProcessId, ParentProcessId, CommandLine
# 종료
... | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
# 기동 (PID 확보)
Start-Process -FilePath <venv python> -ArgumentList <args> -WorkingDirectory <root> `
  -RedirectStandardOutput "logs\e2_run.log" -RedirectStandardError "logs\e2_err.log" `
  -WindowStyle Hidden -PassThru
```

기동 후 **반드시 프로세스 목록을 다시 찍어 봇 본체 1개 + WS 워커 1쌍인지 확인한다.**
(venv 런처 shim 때문에 봇 하나가 PID 2개로 보이는 것은 정상 — 부모/자식 관계로 구분)
로그는 cp949 로 기록된다. Bash 에서 볼 때는 `iconv -f cp949 -t utf-8`.

## 44. e2 추가진입 버그 (2026-08-20 밤 수정)

**증상:** 1차 진입은 나오는데 2차/3차 추가진입이 전혀 안 보였다.

**원인:** `scripts/scalp_bot_e2.py` 에서 1차 신규 진입 직후
`pd["done"] = len(pd["legs"])` 다음에 `pending.pop(sym, None)` 를 해버려,
다음 봉에서 EMA10/EMA15 를 터치해도 추가진입 경로
`sym in positions and pending[sym]` 로 들어가지 못했다.

즉 구현이 사실상 "같은 순간 한 번에 여러 차수 터치한 경우"만 허용하고,
원안의 "1차 후 나중에 2차, 그 후 3차" 를 막고 있었다.

**수정:** 1차 진입 후에는 `pending` 을 지우지 않고 유지한다.
청산/정배열 붕괴/타임아웃 쪽에서만 정리한다.

**의미:** 2026-08-20 저녁까지 관찰한 "2차가 한 번도 안 나옴"은 단순 레짐 문제가 아니라
구현 버그 영향이 컸을 가능성이 있다. 수정 후 표본은 이전과 직접 비교할 때 주의할 것.

## 45. e2 WS 예열 고정 100초 제거 (2026-08-20 밤 수정)

기존 e2 는 WS 워커를 띄운 뒤 `time.sleep(100)` 으로 메인 루프 전체를 멈췄다.
이 동안은:
- 신규 진입
- 2차/3차 추가진입
- BB/RR/TIME_STOP 청산
- 텔레그램 버튼 처리
가 전부 100초 지연됐다. 거래소측 STOP 만 살아 있었다.

**수정:** 고정 sleep 을 없애고, 다음 규칙으로 바꿨다.

1. 최대 대기 100초
2. 2초 간격 점검
3. 앞 10심볼 중 8개 이상이
   `has_sufficient_history(30)` and `is_fresh(90)` 이면 즉시 시작
4. 100초까지 못 채우면 **경고 후 강제 진행**

**운영 의미:** WS 준비 전에도 메인 루프는 돈다. 다만 준비 전에는
**보유 포지션 관리만 허용**하고, 신규 진입과 2차/3차 추가진입은 막는다.
즉 재시작 직후에도 STOP/BB/RR/TIME_STOP 관리와 텔레그램 버튼은 살고,
신규 투입만 준비 완료 후 열린다.

**텔레그램 문구:**
- `WS 워커 기동 - 준비 상태 확인 시작 (최대 100초). 준비 전에는 보유 포지션 관리만 하고 신규/추가 진입은 막습니다`
- `WS 준비 완료 x/10 - 실시간 스캔/신규 진입 재개`
- `경고: WS 준비 미완료 x/10 - 최대 대기 100초 도달, 강제 진행`

## 46. `--max-hold-sec` 최종 결론: 빼는 것이 맞음 (2026-08-20)

## 47. 슬롯 기회비용 검증: TIME_STOP 으로 슬롯을 비워도 더 잃는다 (2026-08-20)

시간손절을 두면 "오래 묶인 슬롯이 빨리 비어 다른 거래를 더 잡을 수 있지 않나"라는 직관은
맞다. 실제로 슬롯 제약 시뮬레이션에서도 **슬롯 점유율은 내려가고 체결 수는 늘었다.**

하지만 지금 e2 는 **거래당 기대값 자체가 음수**라서, 그렇게 더 잡은 거래들이 손실을
추가했다. 즉 현재 단계에서 슬롯을 빨리 회전시키는 것은 효율 개선이 아니라 **손실 가속**이다.

### 조건

- 85심볼, 10일
- 슬롯 3개 제약
- 시간순 선착순 배분
- `--min-risk-pct 0.35` 포함한 현재 e2 계열 비교 맥락

### 결과

| 설정 | 체결 | 버림 | 거래당 | 총액 | 슬롯점유 |
|---|---|---|---|---|---|
| 무제한 | 8,374 | 3,321 | -0.1945% | -1,628.6% | 53.8% |
| 300초 | 9,982 | 1,713 | -0.1954% | -1,951.0% | 38.0% |
| 300초 손실중만 | 9,492 | 2,203 | -0.1901% | -1,804.8% | 42.8% |
| 180초 | 10,650 | 1,045 | -0.1982% | -2,111.2% | 30.9% |

### 해석

1. **메커니즘 자체는 예상대로 작동했다.**
   300초로 자르면 슬롯 점유율이 53.8% -> 38.0%로 떨어졌고, 놓치던 신호 1,608건을 더 잡았다.
   180초는 2,276건을 더 잡았다.

2. **문제는 그 추가 체결이 전부 손실 기대값이라는 점이다.**
   총액이 -1,628.6% -> -1,951.0%로 더 나빠졌다. 거래를 더 많이 할수록 더 많이 잃었다.

3. **슬롯 5개, 8개에서도 방향은 같고 차이만 줄었다.**
   슬롯 제약이 느슨해질수록 TIME_STOP 이 할 일이 줄어드는 구조라서 그렇다.

4. **현재 라이브도 슬롯 부족 상태가 아니다.**
   라이브 원장 실측 슬롯 점유율은 약 39.5%였다. 관측 2.23시간 동안 슬롯 3개의 총 가용시간
   6.7시간 중 2.65시간만 사용했다. 슬롯의 약 60%가 비어 있었다.

### 운영 결론

- "20분 묶인 슬롯이 아깝다"는 직관만으로 슬롯 수를 늘리거나 TIME_STOP 을 넣지 말 것
- 거래당 기대값이 음수인 동안에는 **슬롯을 비우는 것 자체가 손실 확대**일 수 있다
- 슬롯 확장 판단은 체감이 아니라 **실측 점유율과 거래당 기대값 부호**로 할 것
- e2 에서 먼저 해결할 것은 슬롯 회전이 아니라 **진입 우위 복원**

## 48. 유령 포지션이 슬롯을 막는 버그: `보유2`인데 실제는 1개 (2026-08-20)

### 증상

- 텔레그램 `e2상태` 가 `보유2` 로 뜨는데, 실제 거래소 포지션은 1개만 열려 있었다.
- 이 경우 `len(positions)` 기준 슬롯 계산이 실제보다 크게 잡혀, 신규 진입이 막히거나
  "왜 슬롯이 계속 1개만 도는가"처럼 보일 수 있다.

실측 당시:

- 거래소 실제 포지션: `BOMEUSDT` 1개
- e2 상태파일: `BOMEUSDT`, `BTWUSDT` 2개

즉 텔레그램 숫자가 틀린 것이 아니라, **봇 내부 보유목록이 거래소보다 1개 많았다.**

### 원인

e2 는 텔레그램 상태와 슬롯 점유를 **거래소 실시간 계좌가 아니라 내부 `positions`/state** 로 센다.
문제는 외부청산/누락 청산 뒤에 그 심볼이 내부 목록에서 즉시 빠지지 않는 경로가 있었다는 점이다.

특히 `bar_align` 대기 중에는 메인 루프가 다시 돌기 전까지 동기화가 늦어져, 유령 포지션이
수십 초 이상 남을 수 있었다.

### 수정

2026-08-20 밤 패치:

1. 거래소 `futures_account()["positions"]` 를 주기적으로 읽어,
   **내부에는 있는데 거래소에는 없는 심볼**을 `외부청산 감지`로 제거한다.
2. 이 동기화를 본 루프뿐 아니라 **`bar_align` 대기 루프 안에서도** 돌린다.
3. 제거 시 `pending`, `unprotected`, `state` 를 함께 정리하고 쿨다운도 건다.

### 운영 확인 포인트

- 텔레그램 `보유N` 이 의심스러우면, 반드시 **거래소 실제 포지션 수와 state 파일**을 같이 본다.
- 패치 후에는 같은 상황에서 텔레그램/로그에
  `외부청산 감지 <심볼> <방향> - 내부 보유목록에서 제거`
  문구가 나와야 정상이다.
- 이 문구가 안 나오는데도 `보유N` 이 계속 거래소보다 크면, 다시 버그로 의심할 것.

### 영향

- 이 버그는 단순 표기 오류가 아니라 **슬롯 잠김 버그**다.
- 실거래 포지션 수보다 `positions` 가 크면, e2 가 스스로 "슬롯이 찼다"고 오판해 신규 진입을
  막을 수 있다.

## 49. 원장/슬롯 `+ROE` 착시 버그: 실체결 손익과 표시 가격이 다른 기준이었다 (2026-08-20)

### 증상

- 텔레그램/슬롯 화면에서 `+ROE` 로 보인 거래가, 원장 `real_net` 기준으로는 손실인 경우가 있었다.
- 일부는 수수료 때문에 생길 수 있는 정상 현상이지만, 일부는 **`realizedPnl` 자체가 음수인데도
  원장 `roe_pct` 가 플러스**로 기록되는 비정상이었다.

실측 예:

- `HEMIUSDT LONG BB` 원장 `roe_pct +6.43%`, `real_realized_pnl -0.093337`
- `BIOUSDT LONG RR` 원장 `roe_pct +8.30%`, `real_realized_pnl -0.1658`
- `LITUSDT SHORT RR` 원장 `roe_pct +4.03%`, `real_realized_pnl -0.0127125`

### 원인

청산 직후 원장 기록에서:

- `real_commission`, `real_realized_pnl`, `real_net` 은 **실제 `futures_account_trades`**
  체결 내역으로 계산했다.
- 하지만 `entry_price`, `exit_price`, `roe_pct`, `nominal` 은 **실체결 평균가가 아니라**
  내부 평단(`pos.entry`)과 청산 시점 마크가격(`mark`)으로 기록했다.

즉 같은 거래 안에서

- 손익(`real_net`)은 체결 기준
- ROE/표시가격은 모델 기준

으로 **기준이 둘로 갈라져 있었다.**

예를 들어 `HEMIUSDT LONG BB` 는 실제 진입 체결가가 약 `0.009385` 였고 청산 체결가는
약 `0.009331~0.009332` 였다. 실제로는 손실이 맞는데, 원장은 내부 평단
`0.009212...` 을 써서 플러스로 보였다.

### 수정

2026-08-20 패치:

1. 청산 직후 `futures_account_trades` 에서 **진입측/청산측 체결을 분리**
2. 각각의 **수량가중 평균 체결가**를 계산
3. 원장 `entry_price`, `exit_price`, `quantity`, `nominal`, `roe_pct` 를
   그 **실체결 스냅샷 기준**으로 기록
4. `real_commission`, `real_realized_pnl`, `real_net` 집계 방식은 그대로 유지

즉 패치 후에는 슬롯/원장/브리핑의 표시용 가격과 실손익이 **같은 체결 집합**을 바라본다.

2026-08-20 추가 패치:

1. 시장가 진입 직후 `entry_fill_after()` 로 **실제 진입 평균 체결가**를 조회한다.
2. `Pos.legs` 에 EMA 지표값 대신 실제 진입 평균가를 넣는다.
3. 2차/3차 추가 진입도 새로 집행된 차수만큼 실제 체결가를 `legs` 에 추가한다.
4. `Pos.entry`, `risk`, `tp_rr`, 보유 중 ROE, `nominal` 이 모두 같은 실체결 기준을 보게 했다.
5. 주문 직전 mark 기준으로 손절선/익절선 통과 및 `--min-risk-pct` 를 한 번 더 검사한다.

### 중요한 해석

- 첫 패치(청산 후 원장 기록)는 **실제 자산 손익을 개선하지 않는다.**
- 추가 패치(진입 후 실제 체결가를 `Pos.entry` 로 사용)는 앞으로의 **라이브 동작 정합성**을 고친다.
- 과거 `real_net` 은 원래도 체결 기반이었기 때문에 이미 발생한 경제적 손익은 그대로다.
- 다만 앞으로는 RR 익절선, 근접손절 가드, 보유 중 ROE 표시가 허수 EMA 평단이 아니라 실제 진입가 기준으로 돈다.

이번 QA에서 확인된 결론:

- `+ROE / real_net -` 중 일부는 수수료 때문에 정상 가능
- 그러나 `+ROE / realizedPnl -` 는 이 버그의 전형적인 증상

### 검증

- `tests/test_scalp_e2_bugs.py` 에 회귀 테스트 추가
  - LONG 체결 평균가로 ROE 부호가 뒤집히는 케이스 (`HEMIUSDT`)
  - SHORT 체결 평균가로 과장된 플러스 ROE가 사라지는 케이스 (`LITUSDT`)
  - 진입 직후 실제 평균 체결가를 전략 평단으로 쓰는 케이스
  - 체결 조회 실패 시 EMA 값이 아니라 주문 직전 mark 가격으로 fallback 하는 케이스
